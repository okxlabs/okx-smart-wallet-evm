# EMERGENCY_PLAN.md — TWA 部署紧急响应预案

## 紧急预案状态：就绪

本预案涵盖 `okx-smart-wallet-dev` SmartWallet 账户在以太坊主网上，账户级别 Transfer-With-Authorization（TWA）功能的生产部署。状态为就绪：响应程序与已审计的合约能力一致（无已确认的严重/高危发现），所有记录的操作手段均为合约实际暴露的真实机制——不含任何虚构的紧急权限。

**能力现实（请先阅读）：** 本系统**无运营商/管理员紧急控制手段**。所有链上操作杆均为账户级别、由用户驱动。主要的运营商可操作响应措施是**链下**（后端 / 风控 / 中继器 / 撮合方）。

## 概述

### 项目
OKX SmartWallet 账户上的账户级别 TWA：EIP-712 签名、一次性、有时间窗口、收款方绑定的 ERC-20/原生资产结算，来源为账户自身余额，并支持收款方门控接收、所有者取消以及 ERC-165 发现。TWA **内联**编译进 `SmartWalletEntry` 实现字节码——TWA 增量不部署任何新合约（DESIGN §14）。

### 链
以太坊主网，**chainId 1**，**Cancun** EVM（EIP-1153 瞬态存储）。Cancun 是硬性前提条件：原生重入瞬态锁无法在非 Cancun 链上运行（DESIGN §12/§14，SECURITY_SPEC §7，RR-1）。构建：solc `0.8.29`，`evm_version=cancun`，`optimizer=true`，`optimizer_runs=100`。

### 风险资产
每个智能钱包账户**自身**的 ERC-20 和原生余额。托管方为账户本身（`from = address(this)`）；**无托管、无资金池、无协议金库、无共享保险库**。TWA 结算将恰好 `value` 转移给签名绑定的收款方；**无协议手续费，无退款路径**。因此：
- 任何单个被攻破的授权或密钥的爆炸半径仅限于**一个账户**的余额——通过本合约不存在跨账户传染。
- 不存在可被耗尽的中央资金池，也不存在运营商可冻结的金库。

### 特权角色
**无——全局范围**。核心能力事实：
- **工厂**（`SmartWalletFactory`）和**实现**（`SmartWalletEntry`）均**无所有者且不可变**。部署时无部署者绑定的特权。
- **无全局暂停、无全局熔断、无全局升级管理员、无代理管理员。**
- 升级采用 **UUPS** 模式，授权由 `_authorizeUpgrade = onlySelf` **按账户**执行——只有账户本身（通过所有者授权的 `execute` / UserOp / 中继器路径）才能升级其自身的实现。
- ERC-4337 **EntryPoint v0.7**（`0x0000000071727De22E5E9d8BAf0edAc6f37da032`）为规范入口；它不在 TWA 结算路径上，对 TWA 不赋予任何紧急权限。
- EIP-2470 **Singleton Factory**（`0xce0042B868300000d44A59004Da54A005ffdcf9f`）是一个仅在部署时使用的无状态 CREATE2 部署器；它不持有任何持续权限，绝不能作为所有者/管理员出现。

账户级别角色（账户所有者 = 已注册的具有管理员/过期时间/钩子设置的 keyHash）由**用户控制，而非运营商控制**，且仅绑定于其自身账户。

### 风险类别
1. **部署前 / 部署完整性风险** — 错误的链、非 Cancun 链、工厂缺失导致 CREATE 地址异常、实现↔工厂接线不匹配、字节码大小回退（EIP-170）、子模块/依赖漂移、错误的构建范围。运营商可控：**广播前中止**。
2. **授权 / 资金流风险（按账户）** — 泄露的所有者密钥或过宽的已签署授权可转移该账户的资金；受签名绑定、nonce 终结性和开放时间窗口的约束。
3. **账户生命周期 / 可用性风险** — M-03 最后一个管理员导致账户砖化；M-04/M-05 ERC-4337 验证活性/恶意干扰。无资金损失；降低账户可用性。
4. **链下控制面风险** — 后端将 Canceled 误核对为 Used（DR-001），或中继器/撮合方继续提交已知错误的授权。
5. **未知合约漏洞** — 审计未发现的缺陷；由于不存在全局开关，响应必然为链下 + 按账户处理。

### 操作假设
- 链下控制（后端 / 风控 / 中继器 / 撮合方）是**已记录的主要**缓解手段（DESIGN §13，SECURITY_SPEC §5/§8）——第一响应者，而非备用手段。
- 后端通过事件区分 **Used 与 Canceled**（`TransferAuthorizationUsed` 对比 `TransferAuthorizationCanceled`），**绝不**将已取消的 nonce 视为已支付（DR-001；SECURITY_SPEC §9 条目 14；CONTRACT_INTERFACE.md）。此处出现回退本身即为一起事故。
- 所有者密钥由账户所有者/用户管理；运营商无法代表他们进行签名、取消或升级。
- 受限（非管理员）密钥预期应**配备消费策略钩子**；无钩子的非管理员密钥进行无约束消费是已接受的、已记录的残余风险（R-7），而非漏洞。
- 部署遵循 `DEPLOY_RUNBOOK.md`，机密仅通过环境变量/机密管理器提供（绝不嵌入或提交）。

## 严重级别与激活规则

| 严重级别 | 定义（以本系统术语表述） | 激活 |
|----------|-------------------------------------|------------|
| **SEV-1（紧急）** | 有可信证据表明账户发生未经授权的资金转移、签名/重放漏洞、TWA 钩子绕过、原生结算重入或已部署账户的存储碰撞；或确认存在具有链上资金影响的未知漏洞。 | 立即。呼叫 `<安全负责人>` + `<智能合约值班>` + `<后端风控值班>`。触发链下冻结（停止中继器/撮合方提交、停止联署、将受影响账户/nonce 加入停用列表）并启动未知漏洞响应手册。 |
| **SEV-2（高危）** | 上线时/上线前发生部署完整性故障（错误链 / 非 Cancun / 接线不匹配 / 大小回退 / CREATE 地址不匹配）；或大范围账户活性故障（M-04/M-05 导致大量 UserOp 被拒绝）；或后端核对回退（DR-001）将已取消 nonce 记录为已支付。 | 数分钟内。若在上线前则**广播前中止部署**；否则呼叫 `<智能合约值班>` + `<后端风控值班>` 并执行相关已知风险预案。 |
| **SEV-3（中危）** | 已确认的审计建议项在无资金损失情况下触发（孤立的 M-01 打包兼容性拒绝、M-03 单账户自砖化、有限的 M-05 燃气恶意干扰）；CI 中于部署后发现依赖/构建卫生漂移（M-02）。 | 当日工作时间内。`<智能合约值班>` 评估；监控并安排修复；无需紧急冻结。 |
| **SEV-4（低/信息）** | 外观/文档问题，或单用户操作失误且具有自助修复手段（用户签署了过宽的时间窗口并希望撤销），无系统性信号。 | 尽力处理。路由至支持；用户使用 `cancel` / 密钥轮换。 |

**激活原则（能力诚实）：** 激活绝不意味着运营商可以*停止合约*。对于每个严重级别，运营商侧的操作为：(a) 链下冻结提交/联署/列表，(b) 沟通通知，(c) 向受影响账户所有者提供账户级别自助手段的指导。不存在全局链上"停止"。

## 未知紧急合约漏洞响应

适用于**以前未知**的漏洞（`AUDIT_REPORT.md` 未发现），疑似允许对已部署账户进行未经授权的资金转移、签名/重放滥用、钩子绕过、重入或存储损坏。

**能力现实——请先阅读。** **不存在**运营商开关可以全局暂停、冻结、升级或清扫用户账户。工厂和实现均无所有者/不可变；UUPS 升级为按账户的 `onlySelf`。唯一即时的运营商可控遏制手段是**链下**的，唯一的链上修复是**按账户、由用户驱动**的。

1. **链下遏制（立即，运营商可控——主要手段）。**
   - `<后端风控值班>` 停止中继器/撮合方提交 TWA 授权（停止 `executeTransferWithAuthorization` / `receiveWithAuthorization` 的联署和提交）。
   - 拒绝联署或中继后续授权；将受影响账户、收款方、代币及任何已知错误 nonce 加入停用列表。
   - 这**不能**阻止第三方将已签署的授权直接提交给 EntryPoint/账户（执行路径为无需许可）。遏制因此是对撮合路径的尽力抑制，而非保证——须向利益相关方明确说明这一点。
2. **安全评估与复现。** `<智能合约值班>` 在**分叉**上复现（依据 `DEPLOY_DRY_RUN.md`）——绝不针对主网账户。确认范围：哪些账户、哪些资产路径（ERC-20 对比原生资产）、是否需要泄露密钥或为密钥无关。
3. **账户级别修复（用户驱动，唯一的链上修复）。**
   - **撤销待处理授权：** 受影响所有者调用 `cancelTransferAuthorization`（所有者签名的 A 形式，或在 `execute`/UserOp 内自调用的 B 形式），以终止任何未使用/待处理的 nonce，使其永远无法结算。不转移资金；对于已知错误的待处理授权，这是最快的用户侧缓解措施。
   - **轮换/移除密钥：** 所有者通过所有者管理功能轮换或移除被攻破的所有者密钥，以切断签名能力（须注意 M-03 最后一个管理员警告）。
   - **按账户 UUPS 升级至修复后的实现：** 如果缺陷在实现逻辑中，文档化的修复方案是由 `onlySelf` 授权的**按账户** UUPS 升级。`<智能合约值班>` + `<安全负责人>` 准备并审查修复后的实现；**每个账户必须自行升级**（所有者授权）。**不存在**将升级推送至所有账户的中央机制——广泛传达升级信息并跟踪采纳情况。
   - **转移资金（所有者自主选择）：** 如果对该账户而言这是最快的方式，所有者可通过普通的所有者授权转账，将其资产转移至安全地址。
4. **沟通通知。** `<沟通负责人>` + `<安全负责人>` 向账户所有者发布指导（可用的手段：取消 / 密钥轮换 / 自行升级 / 提款），并明确声明运营商无法代表所有者执行这些操作。
5. **停止部署新账户**至已知存在漏洞的实现：在发布修复后的实现之前，门控新的工厂部署。

## 已知风险响应预案

所有条目均为**经审计确认的建议项，无已确认的严重/高危发现，也无已证实的直接资金损失**（`AUDIT_REPORT.md`），在此作为监控 / 人工确认 / 残余风险处理。

### M-03 — 最后一个管理员被移除/降级可能导致账户自调用管理功能砖化（按账户）
- **描述：** 账户管理员可通过 `updateOwner`/`removeOwner` 移除最后一个活跃管理员，此后该账户将无法再执行 `onlySelf` 管理操作——所有者恢复、配额批准、**UUPS 升级**、空签名自取消。仅限单账户；无资金损失。
- **此处的重要性：** 自砖化账户将失去其自身的 UUPS 升级手段，因此上述"按账户升级至修复后实现"的修复措施对其可能不可用。
- **监控：** `<后端风控值班>` 监控所有者生命周期事件，关注导致账户无已注册、未过期管理员密钥的转换。
- **响应：** 在工具中向用户发出警告，提示移除/降级最后一个管理员的风险；保留至少一个活跃管理员。已砖化的账户仅能通过文档化的可恢复自密钥模式进行恢复（**前提是配置了该模式**）；否则管理恢复不可能实现，账户仅限于其剩余的非管理员能力。应向所有者诚实说明这一点。
- **残余风险：** 已接受；缓解措施为运营性的（配置 + UI 防护 + 监控）。

### M-04 — 过期所有者的 UserOp 在 ERC-4337 验证中使用 `block.timestamp`（活性/兼容性）
- **描述：** 对于过期所有者，验证逻辑基于 `block.timestamp` 进行分支，而非通过验证数据返回过期时间；合规打包器可能拒绝本应有效的 UserOp。**无资金损失。**
- **监控：** 跟踪过期所有者配置的打包器拒绝率 / UserOp 失败遥测。
- **响应：** SEV-3（若出现大范围活性损失则为 SEV-2）。链下缓解（打包器/中继器策略，在适当情况下建议使用非过期密钥）加上计划中的代码修复（将有效过期时间打包进验证数据）。无需紧急操作，无资金敞口。
- **残余风险：** 已接受，持续监控。

### M-05 — 内置验证器在验证期间可能回滚 / 执行无限制的证明工作（燃气/模拟恶意干扰）
- **描述：** 格式错误的 ECDSA/passkey 载荷在解码时可能回滚；大型证明数组产生无本地上限的线性验证工作。影响 = 受 `verificationGasLimit` 和打包器策略约束的燃气/模拟恶意干扰；**无资金损失**。
- **监控：** 关注异常的验证燃气 / 模拟失败模式及可枚举 keyHash 探测。
- **响应：** SEV-3。当前在打包器/中继器侧进行速率限制和燃气策略控制；后续安排修复（失败关闭解码 + 证明长度上限）。无需紧急冻结。
- **残余风险：** 已接受，持续监控。

### M-01 — 非规范的 `SIG_VALIDATION_FAILED` 打包（打包器兼容性）
- **描述：** 签名失败的验证数据被打包进错误的 ERC-4337 字段；**无效的** UserOp 可能被误分类为基于聚合器的。仅为打包器兼容性 / 模拟误导；**无资金损失**。
- **监控：** 纳入打包器兼容性回归监控。
- **响应：** SEV-3；安排代码修复（使用规范的 `1`）。无需紧急操作。
- **残余风险：** 已接受，持续监控。

### 原生收款方重入（审计已驳斥；残余风险 = 锁的正确性）
- **描述：** 原生结算将 ETH 发送至可重入的用户控制收款方。审计**驳斥**了可利用性：受 CEI nonce 先写后转的约束、全跨度瞬态（EIP-1153）重入锁、经检查的低级调用、钩子包装及自调用防护的共同约束；重入测试已覆盖。
- **依赖：** 防护**需要 Cancun**（EIP-1153）——将此残余风险与部署前提条件相耦合（见停止条件）。
- **监控/响应：** 不预期发生活跃事故。重入形态异常视为潜在未知漏洞（SEV-1 路径）并在分叉上进行验证。在交接中保留原生重入测试和委托并回滚模拟器文档。
- **残余风险：** 低（仅限锁的正确性），已接受。

### R-7 — 无钩子非管理员密钥可无限制消费（已接受的配置残余风险）
- **描述：** 没有钩子的非管理员密钥可通过 TWA 消费该账户的资产，与今日通过 `execute` 消费完全相同。审计确认这**不是绕过**，而是已接受的配置残余风险。
- **响应：** 运营性——配置时必须为受限密钥附加消费策略钩子。监控配置时未附带钩子的受限密钥。本身不构成事故。

### DR-001 — 后端不得将 Canceled 视为已支付（核对安全性）
- **描述：** Used 和 Canceled 均设置相同的链上 `bool`；`transferAuthorizationState`/`AuthorizationAlreadyUsed` 无法区分二者。仅有事件 `TransferAuthorizationUsed`（结算证明）对比 `TransferAuthorizationCanceled`（撤销证明）可以区分。
- **此处的重要性：** 链下冻结手段（取消 + 停用列表）**依赖**于后端遵守此规则。如果后端将已取消 nonce 记录为已支付，则 `cancel` 作为撤销控制手段将失效。
- **监控/响应：** 验证核对逻辑区分了两种事件（SECURITY_SPEC §9 条目 14；CONTRACT_INTERFACE.md）。回退即为事故（SEV-2）：暂停结算记账，修正核对逻辑，并在恢复前从事件重新推导状态。

## 特定于部署的紧急 / 停止条件

上线前及上线时的中止门控。当任何条件成立时，`<部署运营商>` 必须**在广播前停止**（不发送部署交易）并升级处置。每项均对应 `DEPLOY_RUNBOOK.md` / `DEPLOY_CHECK.md` / `DEPLOY_DRY_RUN.md` 中的检查项。

1. **错误链 / 非 Cancun 链——硬性停止。** 绝不部署至非预期目标链，也绝不部署至未激活 Cancun/EIP-1153 的链。原生重入瞬态锁在 Cancun 之前不受支持（DESIGN §12/§14，SECURITY_SPEC §7，RR-1）。广播前确认 `chainId == 1` 且已激活 Cancun。非 Cancun 的部署无法就地恢复。
2. **工厂缺失 + 意外 CREATE 地址。** 部署假设 EIP-2470 工厂存在于 `0xce0042B868300000d44A59004Da54A005ffdcf9f`（CREATE2，确定性地址）。若在预期使用 CREATE2 的链上该工厂意外缺失，或预测的 CREATE2 地址与实际部署地址不一致，则**停止**。先重新确认工厂存在性、salt 及 initCode（相同编译器设置）。
3. **实现↔工厂接线不匹配。** 部署 `SmartWalletEntry` 后再部署 `SmartWalletFactory(impl)`，断言 `SmartWalletFactory.IMPLEMENTATION() == <已部署的 SmartWalletEntry 地址>`。若工厂指向错误（或零）实现，则**停止并重新部署**——它创建的每个账户都会接线至错误实现。同时断言 `entryPoint() == 0x0000000071727De22E5E9d8BAf0edAc6f37da032` 和 `supportsInterface(0x86c5a9e1) == true`，并确认单例工厂永远不是任何所有者/管理员（根据无所有者设计该情况不适用，通过缺失来断言）。
4. **字节码大小回退（EIP-170）。** `SmartWalletEntry` 运行时为 24,510 字节——仅比 24,576 的限制少 66 字节（本阶段已验证）。在部署前立即重新运行 `forge build src script --sizes`。若运行时超过 24,576，或任何源码增长已侵蚀 66 字节的余量而未重新调整 `optimizer_runs` / 大小缓解措施，则**停止**。
5. **子模块 / 依赖漂移。** 打包前核对 `lib/` gitlink，并**离线**构建（`FOUNDRY_OFFLINE=true`），以防止 forge 自动运行 `git submodule update` 并重置已漂移但可用的库（此仓库的已知陷阱）。若库无法核对至已审计修订版本，或构建改变了子模块状态，则**停止**。
6. **错误构建范围（M-02）。** 默认 `forge build` 在 `test/Recovery.t.sol` 上失败（继承了私有 `smart-wallet-recovery` 依赖）。部署验证必须使用 `forge build src script`（可通过）或恢复私有依赖。若部署/CI 步骤依赖于无范围限定的默认构建并失败，则**停止**——修复构建范围，不得跳过验证。
7. **Salt / 跨链确定性未锁定。** 运营商提供的 `DEPLOY_FACTORY_SALT`（bytes32，来自环境变量）必须被记录；相同的 salt + 相同的 initCode + 工厂存在，是实现任何预期跨链相同地址的必要条件。若在需要确定性地址时 salt 未设置/未记录，则**停止**。
8. **干运行未通过。** 若分叉干运行（`DEPLOY_DRY_RUN.md`）——创建账户 → ERC-20 结算 → 重放回滚、存储布局无碰撞——未在目标等效分叉上通过，则**不得上线**。（本阶段内的干运行仅因未配置分叉 RPC 而延期；运营商必须在主网广播前执行该计划。）
9. **机密 / 静态检查违规。** 若任何部署制品中嵌入了私钥或 RPC URL 字面量，在未注释行上携带了 broadcast/verify/private-key 标志，或将记录/提交机密，则**停止**。机密仅来自环境变量/机密管理器。在广播前重新执行捆绑的机密/静态检查，确保结果干净。

**广播中/后注意事项：** 若停止条件在广播**后**才被发现（例如部署后发现接线不匹配），已部署的工厂/实现为不可变且无所有者——无法就地暂停或修补。响应措施为：(a) 不宣传或向有问题的部署引导账户，(b) 在新地址部署修正后的实现/工厂，(c) 传达规范地址。已针对有问题实现创建的账户只能通过其自身的 `onlySelf` UUPS 升级进行修复（受 M-03 约束）。

## 恢复与恢复服务条件

仅当**所有**适用条件满足时，方可恢复部署验证 / 上线（或事故后恢复撮合 TWA 服务）：

1. **触发原因已解决。** 停止条件/事故根本原因已修复并验证（正确链/Cancun；预测 == 实际 CREATE2 地址；`IMPLEMENTATION()` 接线正确；大小 ≤ 24,576 且有余量；子模块已核对；通过 `forge build src script` 构建干净）。
2. **部署后断言通过（只读）。** `SmartWalletFactory.IMPLEMENTATION() == SmartWalletEntry`；两个地址均有非零代码；`SmartWalletEntry.supportsInterface(0x86c5a9e1) == true`；`entryPoint() == 0x0000000071727De22E5E9d8BAf0edAc6f37da032`；`TRANSFER_AUTHORIZATION_DOMAIN_SEPARATOR()` 等于账户域分隔符；存储布局显示与 `0x653ff6dc…` 无碰撞。
3. **干运行通过。** 分叉干运行（账户创建、ERC-20 结算、重放回滚）在目标等效分叉上通过。
4. **链下控制已验证。** 后端 Used 与 Canceled 核对（DR-001）已确认正确；停用列表准确；仅在 `<后端风控值班>` 确认无已知错误授权仍未撤销后，才重新启用中继器/撮合方提交。
5. **按账户修复已跟踪（若发生 SEV-1/未知漏洞事件）。** 已发布修复后的实现，已传达升级指导，且采纳情况已跟踪；仅在修复后的实现发布后才重新启用新账户部署。
6. **审批确认。** `<安全负责人>`（安全事件）和 `<部署运营商>`（部署完整性停止）各自记录明确的恢复/继续决定及支撑证据。

**恢复诚实说明：** 由于不存在全局暂停，"恢复"意味着恢复链下撮合服务和/或新账户部署——不存在需要取消暂停的链上全局状态。各个账户始终由其所有者独立管理。

## 证据保全要求

在任何可能覆盖状态的修复措施执行前，为每起事故及每次中止/完成的部署保全以下内容。**不得**将机密（私钥、令牌、RPC URL）纳入证据；仅通过环境变量名称引用。

1. **部署记录：** 确切的构建命令、`forge`/solc 版本、`evm_version`、`optimizer_runs`、`--sizes` 输出（含已记录的 SmartWalletEntry 大小和余量）、使用的 `DEPLOY_FACTORY_SALT` 值、预测与实际 CREATE2 地址、部署交易哈希、chainId/Cancun 确认，以及构建前后的 `lib/` 修订版本状态。
2. **部署后断言输出：** 恢复 §2 中的只读检查（工厂↔实现接线、代码存在性、`supportsInterface`、`entryPoint`、域分隔符、存储布局差异）。
3. **事故时间线：** 检测时间、呼叫了哪些人员、采取的行动（链下冻结切换、停用列表变更）以及带时间戳的决策节点。
4. **链上证据：** 受影响账户地址、相关交易哈希，以及——至关重要的——用于按 DR-001 重建每个 nonce 的 Used 与 Canceled 状态所需的相关**事件**（`TransferAuthorizationUsed`、`TransferAuthorizationCanceled`、所有者生命周期事件）。在涉及 ERC-4337 路径（M-04/M-05）时，捕获区块范围和 EntryPoint UserOp 哈希。
5. **复现制品：** 用于复现疑似漏洞的分叉区块号及干运行 / 复现脚本或记录（依据 `DEPLOY_DRY_RUN.md`），以确保分析可重放。
6. **后端/控制面状态：** 中继器/撮合方提交日志（已脱敏）、停用列表快照，以及证明事故发生时 Canceled 与 Used 如何分类的核对输出。
7. **沟通记录：** `<沟通负责人>` / `<安全负责人>` 发布的利益相关方/用户通知及任何披露声明的副本。
8. **保管链与留存：** 将证据存储在防篡改、访问受控的位置，并遵守策略规定的留存期限；记录每件制品的收集人和时间。证据中不得含有敏感凭据。
